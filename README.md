# WP Site Hardening

Hardening for any WordPress site. One plugin, four jobs:

1. **Disable XML-RPC** — `/xmlrpc.php` returns 403, methods are emptied, RSD / WLW manifest links and the `X-Pingback` header are removed.
2. **Disable feeds** — `/feed/` and `/comments/feed/` redirect to the home page (301 by default, or 404 if you pick it), and feed links are removed from `<head>`.
3. **Fully disable the REST API by default** — every request to `/wp-json/` gets 403, including authenticated ones. Switch it back on when you need it.
4. **Custom admin login URL** — the login page moves from `/wp-login.php` to a randomly generated slug, e.g. `https://example.com/login-a1b2c3d4e5/`. Direct `/wp-login.php` requests are redirected to the home page.

## REST API: fully closed by default, open it when you need it

| Mode | Anonymous `/wp-json/` | Logged-in / API-key `/wp-json/` |
| --- | --- | --- |
| Fully disable for everyone (default) | 403 | 403 |
| Restrict to authenticated requests | 401 | Works |
| Off | As WordPress default | Works |

The default is **fully disabled**, as intended: the API stays closed until the site owner switches it back on in Settings → WP Site Hardening.

### Working with WP API Key Authentication

This plugin is designed to work with [WP API Key Authentication](https://github.com/hklcf/wp-api-key-authentication) (same author). Download it from that repo: **Code → Download ZIP**, or clone it, or download the versioned zip from its **Releases** page once a release is published.

- That plugin runs `determine_current_user` at priority 20. This plugin checks the REST API at priority 30, so a valid API key is recognised as authenticated before this check runs.
- In **authenticated only** mode, a valid API key passes and API publishing works, while anonymous requests still get 401.
- In **fully disabled** mode, even a valid API key gets 403. That is deliberate: fully disabled means fully disabled.

So the workflow is: leave it fully disabled most of the time; when you need to publish or read via the API, switch to **authenticated only**, do the work, then switch back to **fully disabled**.

## Installation

1. Copy the `wp-site-hardening` folder into `wp-content/plugins/`.
2. Activate **WP Site Hardening** in WordPress admin.
3. Open **Settings → WP Site Hardening** and check the login URL. Bookmark it.

No configuration is required — the defaults are the recommended ones. The login slug is randomly generated on activation, so there is no fixed default slug to guess.

## Settings

Settings → WP Site Hardening:

- **XML-RPC** — on by default. Off only if you need Jetpack, an old mobile app, or pingbacks.
- **Feeds** — on by default. Choose 301 redirect to home, or 404.
- **REST API** — `fully_disabled` by default (see table above).
- **Custom login URL** — on by default, slug randomly generated on activation (e.g. `login-a1b2c3d4e5`). Change it any time, or press **Generate new random slug**; the old slug stops working immediately. Use 3–100 lowercase letters, digits, hyphens or underscores. `login`, `admin`, `wp-admin`, `wp-json`, `feed` and `comments` on their own are reserved.

## After activation, what changes

| Before | After |
| --- | --- |
| `https://example.com/wp-login.php` | Redirects to home page |
| `https://example.com/wp-admin/` (logged out) | Redirects to the custom login URL |
| `https://example.com/login-a1b2c3d4e5/` | Login page |
| `https://example.com/xmlrpc.php` | 403 |
| `https://example.com/wp-json/` | 403 (default) |
| `https://example.com/wp-json/` (authenticated only mode, logged in / API key) | Works |
| `https://example.com/feed/` | 301 to home page |
| `https://example.com/comments/feed/` | 301 to home page |

Login, logout, lost-password and password-reset links generated by WordPress are rewritten to the custom slug automatically. Password-protected posts keep working.

## Locked out? Recovery

If you forget the custom slug, you are not locked out permanently. Add this line to `wp-config.php`:

```php
define( 'WP_SITE_HARDENING_DISABLE_HIDE_LOGIN', true );
```

Then `/wp-login.php` works normally again. Fix the slug in Settings → WP Site Hardening, then remove the line.

Deactivating the plugin also restores `/wp-login.php`. Deleting the plugin removes its settings; deactivating alone leaves them in place.

## What this plugin does NOT do

- No rate limiting, no firewall, no login-attempt limiting. Keep a firewall or rate limiter in front of an internet-facing site.
- No brute-force protection beyond hiding the login URL. Use a strong password and, ideally, two-factor authentication.
- Hiding the login URL is obscurity, not authentication. It reduces automated scanning; it does not replace a strong password.

## Changelog

### 1.0.3

- Settings page: "WP API Key Authentication" is now a link to https://github.com/hklcf/wp-api-key-authentication, in the intro paragraph and in the REST API description, so it can be downloaded from GitHub.

### 1.0.2

- Fix: rewrite rules were flushed in the settings save handler, but `init` had already run with the old settings, so turning hide-login off flushed the old slug rule back into the database and the old login URL kept working. Flush is now deferred to the next `init`, and a stale slug rule is cleaned up automatically when hide-login is off.

### 1.0.1

- Fix: load `wp-login.php` with its variables in global scope. The 1.0.0 version included it inside a closure, so `login_header()` saw a stale global `$action` (body class `login-action-delete_attachment`) and the login form showed "Undefined variable `$user_login` / `$error`" warnings with warning HTML injected into the username field. The custom login page now renders cleanly, exactly as the normal login page.

### 1.0.0

- Disable XML-RPC (filter + hard 403 + header/link removal).
- Disable feeds (`/feed/`, `/comments/feed/`, all feed types) with 301 or 404.
- REST API: fully disabled by default, authenticated-only mode for use with WP API Key Authentication.
- Custom login URL with randomly generated slug on activation, rewrite rule, `login_url` / `logout_url` / `lostpassword_url` / `register_url` / `site_url` rewriting, and `wp-config.php` escape hatch.
- Settings page under Settings → WP Site Hardening.
